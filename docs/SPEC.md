# Техническое задание: RL-среда для финансового аудита (`FinAudit-RL`)

**Мероприятие:** REC GENESIS Hackathon // FinTech (онлайн-отбор)
**Дедлайн сдачи:** 22 ноября 2026 года, 23:59 (время Астаны)
**Режим разработки:** автономный Python-пакет с офлайн-проверкой в Docker

## 1. Цель и границы проекта

Создать воспроизводимую, изолированную RL-среду с синтетическим генератором бухгалтерских данных, узким инструментальным интерфейсом расследования и формальной функцией награды для оценки и потенциального дообучения ИИ-аудиторов.

### Что входит в объём работ

* Детерминированный генератор компаний (чистая сбалансированная история, отвлекающие корректные кейсы, 4 базовых типа ошибок и 2 взаимодействующих сценария).

* Независимый аудиторский валидатор сгенерированных эпизодов (проверка балансов до мутации, расхождений после и достаточности доказательств).

* Слой безвредных преобразований (перестановка записей и биективный ремаппинг ID) для парных проверок инвариантности.

* Изолированная RL-среда с JSON-контрактом `reset` / `step` в стиле Gymnasium, 5 инструментами и разделением процесса агента и оценщика.

* Открытый matcher, расчёт метрик (`P`, `R`, `F1`) и терминальной награды с тестами против specification gaming.

* Четыре адаптера базовых политик, 10 `train`- и 10 `dev`-эпизодов, `trajectories.jsonl`, автотесты `pytest`, Dockerfile, README и записка о дизайне (`DESIGN.md`).

### Что намеренно исключено

* Обучение весов RL-модели, подключение GPU, LLM/платных API и выход в сеть.

* Веб-интерфейс, платёжные интеграции, чат-бот или использование любых реальных персональных и финансовых данных.

### Технические ограничения

* **Среда исполнения:** Python 3.11, 2 CPU, 4 ГБ RAM, без GPU, без интернета.

* **Ограничения на решение и прогон:** общий размер решения не более 1 ГБ; лимит на эпизод — максимум 100 шагов и 60 секунд.

* **Зависимости:** нулевые внешние runtime-зависимости — только стандартная библиотека Python 3.11 (`dataclasses`, `decimal`, `csv`, `json`, `random`, `zoneinfo`, `unittest`); `pytest==8.3.3` опционален.

## 3. Формат эпизода и схемы данных

Один эпизод соответствует одной вымышленной компании и одному отчётному периоду.
**Рекомендуемые диапазоны:** 200–2000 проводок (`ledger.csv`), 20–200 документов (`invoices.jsonl` + `payments.jsonl`), 0–12 скрытых ошибок.

### Общие правила форматов

* **Время:** строки ISO-8601 с явным смещением часового пояса (например, `2026-03-31T23:45:00+05:00`).

* **Деньги:** целые числа в минимальных единицах валюты (`*_minor: int`) с явной разрядностью в `manifest.json` (`currency_exponents`, например `USD: 2`, `EUR: 2`, `KZT: 2`, `JPY: 0`). Использование `float` в расчётах запрещено.

* **FX-курсы:** десятичные строки (`"485.2500"`), вычисления выполняются строго в `decimal.Decimal` с правилом округления из `policy.json`. Сравнение сумм в разных валютах без конвертации запрещено.

* **Отсутствующие ссылки:** явный `null` в JSON и пустое поле в CSV (парсится в `None`), без угаданных связей.

### Открытые файлы эпизода (доступны агенту через инструменты)

| Файл | Поля | Назначение | 
| ----- | ----- | ----- | 
| `manifest.json` | `schema_version`, `episode_id`, `base_currency`, `currency_exponents`, `period_start`, `period_end`, `timezone`, `counts` (`ledger`, `invoices`, `payments`, `fx`), `rounding_rule`, `amount_tolerance_minor` | Метаданные эпизода и параметры расчётов | 
| `policy.json` | `fx_rate_date_rule` (`invoice_issue_date` или `payment_date`), `period_boundary_rule` (`inclusive_start_exclusive_end` по `timezone` компании), `rounding_mode` (`ROUND_HALF_UP` / `ROUND_HALF_EVEN`), `amount_tolerance_minor` | Учётная политика компании | 
| `ledger.csv` | `row_id`, `timestamp`, `account`, `debit_minor`, `credit_minor`, `currency`, `entity_id`, `invoice_id`, `payment_id` | Главная книга проводок | 
| `invoices.jsonl` | `doc_id`, `invoice_id`, `entity_id`, `issued_at`, `due_at`, `currency`, `total_minor`, `line_items` | Первичные счета-фактуры | 
| `payments.jsonl` | `doc_id`, `payment_id`, `timestamp`, `currency`, `amount_minor`, `invoice_refs` | Банковские/платёжные документы | 
| `fx.csv` | `date`, `source_currency`, `target_currency`, `rate` | Курсы обмена валют по датам | 

### Закрытые файлы оценщика (недоступны агенту)

| Файл | Поля | Назначение | 
| ----- | ----- | ----- | 
| `truth.json` | `episode_id`, `issues: [{issue_id, type, affected_ids, expected_amount_minor, currency, acceptable_evidence_sets}]` | Эталонный список ошибок и допустимых наборов доказательств | 
| `provenance.json` | `episode_id`, `config_version`, `clean_balance_check`, `distractors`, `mutations: [{issue_id, type, before, after, causal_note}]`, `transform_applied` | Причинная история генерации и аудит корректности данных | 

## 4. Модель генератора, отвлекающие кейсы и сценарии ошибок

### Этап 1. Чистая согласованная история компании

Генератор создаёт сбалансированный граф хозяйственных операций (поставщики/клиенты, счета, платежи, FX-таблица на весь период с запасом ±7 дней). Для каждой операции соблюдаются:

* двойная запись (`sum(debit_minor) == sum(credit_minor)` в базовой валюте на уровне транзакции и всей книги);

* точное соответствие сумм счетов сумме `line_items`;

* точное соответствие платежей и проводок в `ledger.csv` с учётом `policy.json` и `fx.csv`;

* принадлежность дат признания отчётному периоду в часовом поясе компании.

### Этап 2. Правдоподобные чистые отвлекающие случаи (`distractors`)

Присутствуют как в чистых, так и в ошибочных эпизодах, чтобы отсечь примитивные эвристики:

1. **Разбитые платежи (split payments):** один счёт оплачен 2–3 корректными частями, сумма которых точно равна `total_minor`.

2. **Легитимные возвраты (refunds / credit notes):** счёт, платёж и документально оформленный возврат со сбалансированными обратными проводками.

3. **Законные повторяющиеся суммы:** регулярные услуги (аренда, подписки) с одинаковым контрагентом и суммой, но разными `invoice_id` и датами выставления/периодами.

### Этап 3. Четыре базовых типа ошибок (независимо включаются в `config`)

| Код типа (`type`) | Механика причинной мутации | Расхождение (`expected_amount_minor`) | Допустимые доказательства (`acceptable_evidence_sets`) | 
| ----- | ----- | ----- | ----- | 
| `duplicate_invoice` | Повторно проведённый счёт с тем же контрагентом, суммой, составом `line_items` и дублирующими проводками в книге (при единственной реальной поставке) | Сумма дублирующего счёта в валюте счёта | `[orig_inv_doc_id, dup_inv_doc_id, dup_ledger_row_ids...]` | 
| `payment_allocation_mismatch` | Платёж не привязан (`invoice_refs` пуст / `payment_id` = `null`) либо распределён частично/не полностью на счёт при несоответствии остатка в книге | Нераспределённая или ошибочно отнесённая дельта в валюте платежа/книги | `[payment_doc_id, invoice_doc_id, related_ledger_row_ids...]` | 
| `fx_rate_or_date_error` | При конвертации операции в базовую валюту взят курс неверной даты (нарушение `fx_rate_date_rule` в `policy.json`) или искажённый курс, не совпадающий с `fx.csv` | Модуль разницы между проведённой и корректной суммой в `base_currency` | `[source_doc_id, ledger_row_id, fx_record_id]` | 
| `cutoff_period_error` | Операция с датой за границей `period_start`/`period_end` (с учётом часового пояса из `manifest.json`) ошибочно включена в текущий период | Сумма ошибочно отнесённой проводки в `base_currency` | `[source_doc_id, ledger_row_id]` | 

### Этап 4. Два сценария взаимодействующих ошибок

1. **Мультивалютный частичный платёж на границе периода (`interacting_fx_partial_cutoff`):** иностранный счёт закрывается частичным платежом в другой валюте около полуночи границы периода (разница часовых поясов сдвигает дату операции за границу периода и одновременно применяется курс неверной даты). Генератор записывает связанные, но однозначно разделимые и доказуемые эталонные ошибки с общими первичными документами.

2. **Дубль счёта с ошибочной конвертацией и частичным распределением (`interacting_dup_fx_allocation`):** дублирующий мультивалютный счёт частично перекрывается платежом и проведён по неверному FX-курсу; простая проверка «повторяющихся сумм» без сверки FX и `invoice_refs` даёт неверную сумму или неполный набор доказательств.

### Этап 5. Слой перестановок и смены ID (`transforms.py`)

Принимает готовый эпизод и `transform_seed`, выполняет:

* перемешивание порядка строк в `ledger.csv`, `invoices.jsonl`, `payments.jsonl`, `fx.csv`;

* биективную замену всех идентификаторов (`row_id`, `doc_id`, `invoice_id`, `payment_id`, `entity_id`) на новые случайные ID в едином стиле;

* синхронное обновление `affected_ids` и `acceptable_evidence_sets` в `truth.json`.

## 5. Контракт RL-среды и модель изоляции

### Программный интерфейс

* `reset(seed: int, config: dict) -> tuple[dict, dict]`
  Возвращает `(observation, info)`. Начальное `observation` содержит: описание задачи, `manifest`, краткую выдержку `policy`, доступные таблицы и `remaining_steps = 100`.

* `step(action: dict) -> tuple[dict, float, bool, bool, dict]`
  Возвращает `(observation, reward, terminated, truncated, info)`.

  * За исследовательские шаги `reward = 0.0`.

  * В режиме `train` при `submit` возвращается терминальная награда.

  * В режиме `eval` (закрытая проверка) `step()` всегда возвращает `reward = 0.0` и не включает диагностику, `truth`, `seed` или подсказки в `observation` / `info`; итоговая оценка вычисляется и сохраняется только в журнале оценщика.

### Список допустимых действий

| Действие | Параметры | Правила и ограничения | 
| ----- | ----- | ----- | 
| `list_records` | `table` (`ledger`, `invoices`, `payments`, `fx`), `cursor: str | null`, `limit: int` | `1 <= limit <= 50`; стабильные детерминированные курсоры; возвращает `items` и `next_cursor` | 
| `get_record` | `table`, `id` | Возвращает одну запись по первичному ID или шаблонную ошибку `RECORD_NOT_FOUND` | 
| `get_document` | `doc_id` | Возвращает документ из `invoices` или `payments` либо ошибку `DOCUMENT_NOT_FOUND` | 
| `calculator` | `expression: str` | Только числа и арифметика (`+`, `-`, `*`, `/`, скобки) через `ast.parse` и `Decimal`; длина выражения ограничена; запрещены переменные, функции, импорты, доступ к файлам | 
| `submit` | `findings: dict` | Завершает эпизод с `terminated = True` | 

### Бюджет, ошибки и изоляция

* Максимум **100 шагов** на эпизод (включая `submit`) и тайм-аут **60 секунд**. При исчерпании шагов или времени: `truncated = True`, итоговый ответ считается пустым (`findings = []`).

* Неизвестное действие, невалидные аргументы, неизвестный ID или синтаксическая ошибка калькулятора возвращают ограниченную ошибку фиксированного формата (`error_code`, короткое `message` без путей и стектрейсов) и расходуют 1 шаг.

* Повторный `step()` после `terminated=True` или `truncated=True` возвращает ошибку `EPISODE_FINISHED` без изменения уже зафиксированной награды.

* **Изоляция процесса:** `isolated_runner.py` запускает агента и оценщика в разных процессах с обменом только JSON-сообщениями; процесс агента не имеет доступа к директории с `truth.json` / `provenance.json` и не получает `seed`.

## 6. Схема выводов, matcher и функция награды

### Формат `findings.json` в `submit`

```
{
  "episode_id": "ep_0001",
  "findings": [
    {
      "type": "fx_rate_or_date_error",
      "affected_ids": ["ROW-0142", "INV-0019"],
      "claimed_amount_minor": 1250,
      "currency": "USD",
      "evidence_ids": ["DOC-INV-0019", "ROW-0142", "FX-2026-03-14-EUR-USD"],
      "explanation": "Применён курс за дату платежа вместо даты выставления счёта."
    }
  ]
}

```

### Лимиты и валидация `findings`

* Не более **30 выводов** в `findings`.

* Не более **10 ID доказательств** (`evidence_ids`) и не более **1000 символов** в `explanation` на каждый вывод.

* При нарушении схемы, несовпадении `episode_id` или превышении лимитов эпизод завершается с `terminated = True`, наградой **`-1.0`** и записью кода ошибки валидации в журнал оценщика.

### Правила сопоставления (`matcher.py`)

1. **Нормализация:** `affected_ids` и `evidence_ids` приводятся к отсортированным множествам уникальных строк; `currency` — к верхнему регистру.

2. **Условие совпадения пары `(finding, truth_issue)`:**

   * точное совпадение `type`;

   * точное совпадение нормализованного множества `affected_ids`;

   * точное совпадение `currency`;

   * `abs(claimed_amount_minor - expected_amount_minor) <= amount_tolerance_minor`;

   * существует хотя бы один набор `req_set` из `acceptable_evidence_sets`, такой что `req_set.issubset(set(finding.evidence_ids))`, и все указанные `evidence_ids` реально существуют в открытых записях эпизода.

3. **Взаимно однозначное сопоставление:** строится двудольный граф допустимых совпадений `(finding_i, truth_j)` и ищется максимальное паросочетание (алгоритм Куна / augmenting paths) с детерминированным лексикографическим тай-брейком по `(truth.issue_id, finding_index)`.

4. **Классификация:** сопоставленные пары — `TP`; несопоставленные и дублирующие выводы — `FP`; несопоставленные эталонные ошибки — `FN`.

### Метрики и формула награды (`reward.py`)

* Точность: `P = TP / (TP + FP)` (при `TP + FP == 0` значение `P = 0.0`).

* Полнота: `R = TP / (TP + FN)` (при `TP + FN == 0` значение `R = 0.0`).

* `F1`:

  * если `len(truth) == 0` и `len(findings) == 0`, то `F1 = 1.0`;

  * если `len(truth) == 0` и `len(findings) > 0`, то `F1 = 0.0`;

  * иначе `F1 = 2 * TP / (2 * TP + FP + FN)`.

* **Терминальная награда:**
  `reward = clip(2 * F1 - 1 - 0.002 * inspection_steps, -1.0, 1.0)`
  где `inspection_steps` — количество исследовательских шагов до `submit`.

## 7. Базовые политики, данные и траектории

1. **`random_explorer`:** детерминированный случайный обход таблиц с фиксированным `seed` и отправкой случайного/пустого ответа.

2. **`simple_reconciler`:** честный скриптовый аудитор, который постранично выгружает открытые записи через инструменты среды, сверяет дубли, FX-курсы, границы периода и привязки платежей с помощью `policy.json` и отправляет доказанные выводы.

3. **`flag_all_attack`:** атакующая политика, которая помечает максимальное число записей/типов, проверяя устойчивость награды к спаму.

4. **`oracle`:** запускается только со стороны оценщика (имеет доступ к `truth.json` в тестовом контуре) и проверяет достижимость максимальной награды и корректность `acceptable_evidence_sets`.

### Обязательные артефакты данных

* `data/train/`: 10 эпизодов (разные валюты, часовые пояса, чистые, базовые и взаимодействующие ошибки).

* `data/dev/`: 10 эпизодов с непересекающимися `seed` и конфигурациями.

* `trajectories/trajectories.jsonl`: записи `{episode_id, step, action, observation, reward, terminated, truncated}` для прогонов базовых политик; автоматический тест гарантирует отсутствие `truth`/`provenance`/`seed` в `observation`.

## 8. План верификации и приёмки (100 баллов)
